## Dataset — batch sizing & packing

|Param|Purpose|Options / meaning|
|---|---|---|
|`per_device_batch_size`|Training batch size per device. Can be fractional (see `expansion_factor_real_data` below for why).|Float, default `12.0`.|
|`expansion_factor_real_data`|Controls how many hosts actually load data vs. how much each loading host reads. When `>1`: `total_hosts // expansion_factor_real_data` hosts load data, each reading `per_device_batch_size * expansion_factor_real_data`. When between `0` and `1`: lets Grain read a checkpoint saved by a job with a larger chip count using a smaller chip count. ([details](https://github.com/AI-Hypercomputer/maxtext/blob/main/docs/guides/data_input_pipeline/data_input_grain.md#using-grain))|Float, default `-1.0` = disabled/not applicable.|
|`eval_per_device_batch_size`|Eval batch size per device.|Float, default `0.0` = not set (falls back to using the training batch size).|
|`max_corpus_chars`|Cap on how many characters of raw corpus text to load (a dataset-size safety valve, mainly for TFDS-style pipelines).|Integer, default `10_000_000`.|
|`train_data_columns`|Which column(s) of the dataset to use as training input. For DPO datasets this would instead point at `"chosen"`/`"rejected"` columns.|List, default `['text']`.|
|`train_image_column`|Column name for image data in multimodal training sets.|String, default `'image'`.|
|`eval_data_columns`|Same as `train_data_columns`, for eval.|List, default `['text']`.|
|`eval_image_column`|Same as `train_image_column`, for eval.|String, default `'image'`.|
|`packing`|Whether to pack multiple shorter examples into a single fixed-length sequence (avoids wasting compute on padding).|`true`/`false`, default `true`.|
|`num_epoch`|Number of epochs to iterate over the dataset.|Integer, default `1`.|
|`generate_padding_batch_train`|Whether to generate a padding batch (dummy batch to keep step counts/shapes consistent) for training.|`true`/`false`, default `false`.|
|`generate_padding_batch_eval`|Same, for eval.|`true`/`false`, default `false`.|
|`max_segments_per_seq`|Maximum number of packed segments allowed in a single sequence. Needs to be passed to TransformerEngine's `DotProductAttention` layer for packing support — TE can crash or corrupt data if more segments are packed than this specifies. Recommended to set to something like `32` for GPUs using TransformerEngine.|Integer, default `-1` (unset/unbounded).|

## Batch-size ramp-up

Analogous to Megatron-LM's batch-size ramp-up ([reference implementation](https://github.com/NVIDIA/Megatron-LM/blob/2a01637aa54ccdaf7ea9afc1f1b80f58c53d7f3c/megatron/core/num_microbatches_calculator.py#L233-L237)): gradually increases the per-device batch size in stages from a smaller starting value up to the final target, rather than starting training at full batch size immediately.

|Param|Purpose|Options / meaning|
|---|---|---|
|`enable_rampup_batch_size`|Master switch for batch-size ramp-up.|`true`/`false`, default `false`.|
|`per_device_batch_size_start`|Starting batch size for the ramp-up.|Float, default `4.0`.|
|`per_device_batch_size_increment`|How much to increase the batch size by at each ramp-up stage. For a clean ramp-up, `(per_device_batch_size - per_device_batch_size_start)` should be evenly divisible by this increment.|Float, default `2.0`.|
|`global_rampup_samples`|Target number of training samples to process during the entire ramp-up phase. No strict constraint on the value — just needs to be positive.|Integer, default `500`.|

### Grain pipeline (`dataset_type: grain`)

Grain is Google's data-loading library; MaxText uses it for high-throughput, deterministic input pipelines. ([Grain guide](https://github.com/AI-Hypercomputer/maxtext/blob/main/docs/guides/data_input_pipeline/data_input_grain.md))

|Param|Purpose|Options / meaning|
|---|---|---|
|`grain_train_files`|Path pattern(s) to Grain training data files. Multiple weighted patterns are supported: semicolon-separated patterns, each with a comma-separated weight — e.g. `"path/to/data1.array_record*,0.3;path/to/data2.array_record*,0.7"`. Note: when using multiple files this way, only ArrayRecord format is supported.|Path pattern string, default `''`.|
|`grain_eval_files`|Same, for eval data.|Path pattern string, default `''`.|
|`grain_train_mixture_config_path`|Path to a JSON file specifying mixture weights for Grain training data (an alternative to inlining weights in `grain_train_files`).|Path string, default `''`.|
|`grain_file_type`|File format for Grain data.|`'arrayrecord'` or `'parquet'`. Default `'arrayrecord'`.|
|`grain_packing_type`|Which packing algorithm Grain uses to pack examples into sequences. |`grain_worker_count`|Number of Grain worker processes for data loading.|Integer, default `1`. |`grain_per_worker_buffer_size`|Per-worker buffer size (training).|Integer, default `1`.|
|`grain_num_threads`|Per-worker, per-dataset thread count. For ArrayRecord, used in Grain's `ReadOptions`. For Parquet, this is the number of files read/interleaved in parallel instead. |`grain_prefetch_buffer_size`|Per-worker, per-dataset prefetch buffer size (training).|Integer, default `500`.|
|`grain_worker_count_eval`|Same as `grain_worker_count`, for eval.|Integer, default `1`.|
|`grain_per_worker_buffer_size_eval`|Same as `grain_per_worker_buffer_size`, for eval.|Integer, default `1`.|
|`grain_ram_budget_mb`|RAM budget (MB) used for the auto-tuning worker-count calculation. Only relevant when `grain_worker_count=-1`.|Integer, default `1024`.|

|`grain_prefetch_buffer_size_eval`|Same as `grain_prefetch_buffer_size`, for eval.|Integer, default `500`.|

|`grain_shuffle_buffer_size`|Shuffle buffer size, used with sequential-access formats like Parquet or TFRecord.|Integer, default `100`.|

## Notes to self

- `dataset_type` is the fork point for this whole section — only one of the TFDS / HF / Grain / OLMo param blocks actually applies at a time, based on this single switch.
- `per_device_batch_size` being a _float_ (not int) is intentional — it's what makes `expansion_factor_real_data` and the ramp-up mechanism work, since effective batch size is computed from this value rather than being a hardcoded integer.
- Grain is clearly the most actively developed pipeline here, given how much deeper its param surface goes (worker tuning, mixture configs, elastic iteration) compared to TFDS or HF — worth defaulting to Grain for any pretraining-scale work where you need serious data-loading throughput.
- `max_segments_per_seq` is one of those params that looks like a training-quality knob but is really about avoiding a TransformerEngine crash/corruption bug — good example of why reading the actual inline comments (not just param names) matters in this file.
