## Qwen3-Next: Gated Delta Net (GDN)

Qwen3-Next replaces standard attention in most layers with **Gated DeltaNet**, a linear-attention variant with a gating mechanism and a delta-rule update — sub-quadratic in sequence length, unlike softmax attention. (Recall from Part 7: GDN's projections shard like `mlp` during training, per the `gdn_head` logical-axis rule.)

|Param|Purpose|Options / meaning|
|---|---|---|
|`gdn_conv_kernel_dim`|Kernel size of the 1D convolution GDN applies before the recurrent update.|Integer, default `4`.|
|`gdn_key_head_dim`|Head dimension for GDN's key/query.|Integer, default `128`.|
|`gdn_value_head_dim`|Head dimension for GDN's value.|Integer, default `128`.|
|`gdn_num_key_heads`|Number of key/query heads.|Integer, default `16`.|
|`gdn_num_value_heads`|Number of value heads.|Integer, default `32`.|
|`gdn_chunk_size`|Chunk size for the parallel-scan algorithm used to compute GDN's recurrence efficiently (chunked parallel scan is what makes linear attention actually fast on accelerators, versus a naive sequential recurrence).|Integer, default `64`.|
|`use_qk_norm_in_gdn`|Whether to L2-normalize query/key tensors inside the Gated Delta Rule kernel.|`true`/`false`, default `true`.|
|`partial_rotary_factor`|Fraction of the head dimension that RoPE is applied to (the rest stays unrotated) — a technique some architectures use to only rotate part of each head's dimensions.|Float, default `1.0` (RoPE applied to the full head dimension).|

## DeepSeek Manifold-Constrained Hyper Connections (mHC)

Hyper Connections generalize residual connections: instead of a single residual stream, the model maintains multiple parallel "streams" that get mixed via a learned (doubly-stochastic) matrix at each layer, rather than the fixed identity connection of a standard residual. "Manifold-constrained" refers to the doubly-stochastic constraint on that mixing matrix, which is what the Sinkhorn-Knopp algorithm below enforces.

|Param|Purpose|Options / meaning|
|---|---|---|
|`mhc_expansion_rate`|Number of parallel residual streams.|Integer, default `1` (i.e. mHC effectively disabled — a single stream is a standard residual connection).|
|`sinkhorn_iterations`|Number of iterations of the Sinkhorn-Knopp algorithm used to project the mixing matrix onto the doubly-stochastic manifold.|Integer, default `20`.|
|`enable_mhc_lite`|Enables **mHC-lite** ([paper](https://openreview.net/pdf?id=5IJX6kvOif)): generates the doubly-stochastic mixing matrix via a permutation-based convex combination instead of running Sinkhorn-Knopp iterations — removes the Sinkhorn cost entirely, but the number of permutation matrices involved scales factorially with `mhc_expansion_rate` (k!), so this is only practical for small expansion rates (e.g. k=4). Recommended whenever the expansion rate is small enough to make the factorial cost acceptable.|`true`/`false`, default `false`.|

## DeepSeek Engram

Engram is a mechanism that augments specific transformer layers with N-gram-based lookup/hashing features — giving the model a form of explicit, non-parametric memory for token sequences, alongside its usual learned parameters.

|Param|Purpose|Options / meaning|
|---|---|---|
|`engram_layers`|Which transformer layer indices have Engram attached. Empty disables Engram entirely. E.g. `[1, 4]` attaches Engram to the 2nd and 5th layers (0-indexed).|List of integers, default `[]`.|
|`engram_max_ngram_size`|Maximum N-gram order covered. E.g. `n=3` covers both 2-grams and 3-grams.|Integer, default `3`.|
|`engram_num_heads`|Number of heads dedicated to Engram.|Integer, default `8`.|
|`engram_head_dim`|Head dimension for those Engram heads.|Integer, default `1280`.|
|`engram_vocab_bases`|Minimum head-vocab sizes for each n-gram order (controls the hash table size per n-gram level).|List of integers, default `[]`.|
|`engram_kernel_size`|Temporal window size for Engram's convolution operation.|Integer, default `4`.|
|`engram_seed`|Seed for Engram's hash mapping (controls how n-grams get hashed into table slots).|Integer, default `0`.|

## Distillation

Knowledge distillation: training a (typically smaller) student model to match a teacher model's outputs, combining a standard task loss with distillation-specific losses.

|Param|Purpose|Options / meaning|
|---|---|---|
|`distill_alpha`|Weight balancing the distillation loss (matching the teacher) against the standard task loss.|Float, default `0.5`.|
|`distill_temperature`|Softmax temperature applied to teacher/student logits before computing the distillation loss — higher temperature softens the probability distribution, exposing more of the teacher's "dark knowledge" about relative class similarities.|Float, default `1.0`.|
|`distill_beta`|Weight for an auxiliary cosine-similarity loss between intermediate activations (specifically, the output-projection activations) of the teacher and student models. `0.0` disables this feature entirely.|Float, default `0.0`.|
|`distill_feature_loss_type`|Which loss function to use for that intermediate-feature distillation.|`"cosine"` or `"l2"`. Default `"cosine"`.|
|`distill_layer_indices`|Which layer indices to apply feature distillation to.|List of integers or `None`, default `None`.|

### Dynamic distillation loss-weight scheduling

Each of `distill_alpha`, `distill_temperature`, and `distill_beta` can optionally be scheduled to change over training, rather than staying fixed — set the corresponding `*_end` value and `*_schedule` shape. Leaving `*_end` as `None` (the default) keeps that weight constant throughout training.

|Param|Purpose|Options / meaning|
|---|---|---|
|`distill_alpha_end`|Target value `distill_alpha` schedules toward, if set.|Float or `None`, default `None`.|
|`distill_alpha_schedule`|Shape of that schedule.|`"linear"`, `"cosine"`, or `"constant"`. Default `"constant"`.|
|`distill_temperature_end`|Target value for `distill_temperature`.|Float or `None`, default `None`.|
|`distill_temperature_schedule`|Shape of that schedule.|`"linear"`, `"cosine"`, or `"constant"`. Default `"constant"`.|
|`distill_beta_end`|Target value for `distill_beta`.|Float or `None`, default `None`.|
|`distill_beta_schedule`|Shape of that schedule.|`"linear"`, `"cosine"`, or `"constant"`. Default `"constant"`.|

## Elastic training

Elastic training lets a job continue running (with a reduced number of slices) if some slices fail or are preempted, rather than the whole job crashing — **Pathways-specific**, and explicitly noted as not working on McJAX (MaxText's non-Pathways multi-controller JAX execution mode).

|Param|Purpose|Options / meaning|
|---|---|---|
|`elastic_enabled`|Master switch.|`true`/`false`, default `false`.|
|`elastic_backup_kind`|Mechanism used to back up state so training can continue elastically after a slice loss.|String, default `"snapshot"`.|
|`elastic_timeout_seconds`|How long to wait for a lost slice before proceeding elastically without it.|Integer, default `300`.|
|`elastic_max_retries`|Maximum number of retry attempts before giving up.|Integer, default `10`.|
|`elastic_min_slice_count`|Minimum number of slices required to continue training — if the slice count drops below this after failures, the job stops rather than continuing further degraded.|Integer, default `-1` = no minimum enforced.|

## Notes to self — and wrap-up for the whole walkthrough

- GDN is Qwen3-Next's answer to the same problem MLA (Part 6) and DSA (Part 6) solve differently: attention's quadratic cost / large KV cache at long context. Worth keeping a mental map of the three approaches side by side: MLA compresses the KV cache via low-rank latents but keeps full softmax attention; DSA keeps full attention's expressiveness but sparsifies which tokens get attended to; GDN abandons softmax attention altogether in favor of a linear-attention recurrence. Three different points on the same trade-off curve.
- mHC and Engram are both genuinely unusual relative to a "standard" transformer — mHC changes the _residual stream topology_ itself (multiple streams + learned mixing, rather than a single fixed-identity stream), and Engram adds _non-parametric_ memory alongside the model's learned parameters. Both are worth reading DeepSeek's own writeups on directly if you want the "why," since this config only tells you the "what."
- `elastic_min_slice_count=-1` (no minimum) is the kind of default that's fine for experimentation but worth revisiting deliberately for any long, expensive pretraining run — training silently continuing on a much-reduced slice count (and therefore much-reduced effective batch size / throughput) without you noticing could quietly change your training dynamics or just waste a lot of wall-clock time before anyone catches it.
- Zooming out across all 13 parts: `base.yml` is really several loosely-coupled subsystems sharing one flat namespace — architecture definition (Parts 3, 4, 6, 12, 13), execution/parallelism strategy (Parts 5, 7), the training recipe itself (Parts 2, 9, 10), data (Part 8), and operational concerns (Parts 1, 9, 10, 11). The biggest practical skill this file rewards is knowing _which_ of those subsystems a given symptom (OOM, slow throughput, loss spike, bad eval numbers) actually lives in, since the fix is almost always in a completely different section than where the symptom shows up.
