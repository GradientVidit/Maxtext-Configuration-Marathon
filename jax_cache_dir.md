## 1. Why does it exist?

XLA (Accelerated Linear Algebra) compiles high-level JAX computation graphs into low-level device binaries optimized for target TPU/GPU hardware. For large models (e.g. 70B+ parameters with complex multi-dimensional sharding), XLA graph compilation can take **15 to 45+ minutes**.

```text
Without Persistent JAX Cache:
  Run 1:  [Graph Build] ──→ [XLA Compile (30 mins)] ──→ [Training Starts]
  Preempted & Restarted:
  Run 2:  [Graph Build] ──→ [XLA Compile (30 mins)] ──→ [Training Starts]  <-- Wasted 30m

With Persistent JAX Cache (jax_cache_dir):
  Run 1:  [Graph Build] ──→ [XLA Compile (30 mins)] ──→ Cache Saved to Disk
  Preempted & Restarted:
  Run 2:  [Graph Build] ──→ [Load Cached Binary (5s)] ──→ [Training Starts] <-- Instant!
```

`jax_cache_dir` configures JAX's persistent compilation cache directory, storing precompiled HLO executables so subsequent launches on identical hardware bypass XLA compilation entirely.

---

## 2. Fundamentals & Mechanics

JAX uses a content-addressed hashing scheme for cached compilations:
1. **Cache Key**: Generated by hashing the input JAXPR graph, hardware target platform, topology descriptor, XLA flags, compiler version, and static shapes.
2. **Lookup**: Before running XLA compilation, JAX checks `jax_cache_dir` for a matching key.
3. **Hit vs. Miss**:
   - **Hit**: The precompiled target binary is read from disk and loaded directly onto accelerator cores.
   - **Miss**: Full compilation executes, and the resulting binary is serialized into `jax_cache_dir`.

```text
JAX Program ──→ Compute Cache Key (hash) ──→ Look in `jax_cache_dir`
                                                   │
                        ┌──────────────────────────┴──────────────────────────┐
                     Cache Hit                                             Cache Miss
                        ↓                                                     ↓
              Load binary from disk                                Compile with XLA (~30 min)
                        ↓                                                     ↓
              Run on TPU / GPU                                      Write binary to `jax_cache_dir`
```

## 3. Options & Configuration

| Value | Meaning |
|---|---|
| `"~/jax_cache"` (default) | Stores cache files in the user's home directory on local host disk. |
| `"/path/to/persistent/ssd"` | Explicit path to a local high-speed SSD or persistent volume. |
| `""` / `None` | Disables persistent compilation caching; recompiles on every process start. |

Default in `base.yml`:
```yaml
jax_cache_dir: "~/jax_cache"
```

---

## 4. Interactions with Other Parameters

- **`hardware` & `compile_topology`**: Any change to hardware generation (e.g., `v5e` to `v6e`) changes the compilation hash and triggers a fresh cache miss.
- **`compile_xla_flags`**: Adding or tweaking compiler flags alters the compilation key.
- **`ici_*` / `dcn_*_parallelism`**: Mesh size adjustments change tensor shapes and communication collectives, resulting in new cached binaries.

---

## 5. Practical Scenarios & Preemption Handling

- **Spot/Preemptible TPU VMs**: When running long pretraining jobs that suffer frequent preemptions, mounting a persistent disk (or shared network volume) to `jax_cache_dir` prevents wasting 30 minutes of accelerator time on every restart.
- **Container Deployments**: If running inside Docker/GKE, ensure `jax_cache_dir` is mounted to a persistent volume; otherwise, container restarts destroy the cache.
- **Stale Cache / Cache Corruption**: If JAX or XLA updates introduce internal ABI bugs, or if compiler flags changed unexpectedly, clearing `rm -rf ~/jax_cache/*` forces a clean recompile.

---

### One-line intuition

> **`jax_cache_dir` saves compiled XLA accelerator binaries to disk so restarts, preemptions, and subsequent runs with identical topologies start training immediately without repeating expensive graph compilations.**
