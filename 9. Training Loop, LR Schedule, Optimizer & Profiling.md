## Learning rate schedule

MaxText supports two schedule shapes, selected via `lr_schedule_type`:

- **`'cosine'`** — inspired by Llama 2's schedule ([paper §2.2](https://arxiv.org/pdf/2307.09288.pdf)): (1) linear warmup from 0 to `learning_rate` over the first `learning_rate_schedule_steps * warmup_steps_fraction` steps, (2) cosine decay down to `learning_rate * learning_rate_final_fraction` by `learning_rate_schedule_steps`, (3) if `steps > learning_rate_schedule_steps`, a constant LR of 0 for the remainder.
- **`'wsd'`** (Warmup-Stable-Decay) — (1) the same linear warmup, (2) a stable phase at `learning_rate` for the bulk of training, (3) decay to `learning_rate * learning_rate_final_fraction` over `learning_rate_schedule_steps * wsd_decay_steps_fraction` steps (decay shape set by `wsd_decay_style`), (4) same trailing zero-LR phase as cosine if applicable.

The trailing zero-LR phase (both schedules) exists so you can measure the fully-trained model's performance more accurately, without a still-decaying LR muddying the picture.

| Param | Purpose | Options / meaning | Deep Dive |
|---|---|---|---|
| `learning_rate` | Peak learning rate. | Float, default `3.e-5`. | [[learning_rate]] |
| `lr_schedule_type` | Which schedule shape to use. | `'cosine'` or `'wsd'`. Default `'cosine'`. | [[lr_schedule_type]] |
| `learning_rate_final_fraction` | Final LR as a fraction of peak LR — applies to both schedule types. | Float, default `0.1`. | [[learning_rate_final_fraction]] |
| `wsd_decay_steps_fraction` | Fraction of `learning_rate_schedule_steps` spent in the WSD decay phase. | Float, default `0.1` (10%). | [[wsd_decay_steps_fraction]] |
| `wsd_decay_style` | Shape of the WSD decay phase. | `'linear'` or `'cosine'`. Default `'linear'`. | [[wsd_decay_style]] |
| `warmup_steps_fraction` | Fraction of `learning_rate_schedule_steps` spent warming up. Applies to both schedule types. | Float, default `0.1`. | [[warmup_steps_fraction]] |
| `learning_rate_schedule_steps` | The length of the schedule itself. Defaults to matching `steps`. Setting it _longer_ than `steps` means training ends before the LR fully decays; setting it _shorter_ means the remaining steps run at LR 0. | Integer, default `-1` = equal to `steps`. | [[learning_rate_schedule_steps]] |

### AdamW parameters

Follows Llama 2's training setup ([paper §2.2](https://arxiv.org/pdf/2307.09288.pdf)).

| Param | Purpose | Options / meaning | Deep Dive |
|---|---|---|---|
| `adam_b1` | β₁ — exponential decay rate for the first-moment (mean) gradient estimate. | Float, default `0.9`. | [[adam_b1]] |
| `adam_b2` | β₂ — exponential decay rate for the second-moment (variance) gradient estimate. | Float, default `0.95`. | [[adam_b2]] |
| `adam_eps` | Small constant added outside the square root in the denominator, for numerical stability. | Float, default `1.e-8`. | [[adam_eps]] |
| `adam_eps_root` | Small constant added inside the square root in the denominator. | Float, default `0.`. | [[adam_eps_root]] |
| `adam_weight_decay` | AdamW's decoupled weight-decay coefficient. | Float, default `0.1`. | [[adam_weight_decay]] |
| `adamw_mask` | List of parameter name regex patterns to _exclude_ from weight decay — e.g. `['bias', '.*norm', '.*ln.*']`, since decaying norm/bias parameters is generally undesirable. | List of regex strings, default `[]`. | [[adamw_mask]] |
| `mu_dtype` | Dtype used to store AdamW's first-moment ("mu") tracking state. | String, default `""` = inherits from `weight_dtype`. (Note: `nu_dtype` for the second moment isn't yet configurable — Optax always inherits it from the weights' own dtype.) | [[mu_dtype]] |

### Muon optimizer parameters

Muon is a newer optimizer (see [optax's implementation](https://github.com/google-deepmind/optax/blob/main/optax/contrib/_muon.py)). It shares `mu_dtype` and `adam_eps` with AdamW above; its `nesterov`, `weight_decay_mask`, and `adaptive` settings use Optax's own defaults rather than exposing separate MaxText config keys.

| Param | Purpose | Options / meaning | Deep Dive |
|---|---|---|---|
| `muon_beta` | Decay rate for the exponentially-weighted moving average of gradients. | Float, default `0.95`. | [[muon_beta]] |
| `muon_weight_decay` | Weight-decay regularization strength, multiplied by the learning rate. | Float, default `0`. | [[muon_weight_decay]] |
| `muon_consistent_rms` | Controls update scaling: `None` applies width-based scaling; a float applies "consistent RMS" scaling instead (the comment recommends `0.2` if you go this route). | `None` or float, default `None`. | [[muon_consistent_rms]] |

## DiLoCo (distributed low-communication training)

DiLoCo trains multiple model replicas mostly independently, synchronizing only periodically — designed for settings where inter-replica bandwidth is limited (e.g. training across geographically separate clusters). The bandwidth-throttling params below are a _testing_ tool for simulating that constrained-bandwidth environment, not something you'd set for a real production run.

| Param | Purpose | Options / meaning | Deep Dive |
|---|---|---|---|
| `enable_diloco` | Master switch for DiLoCo. | `true`/`false`, default `false`. | [[enable_diloco]] |
| `diloco_sync_period` | How many local steps each replica takes between synchronization rounds. | Integer, default `36`. | [[diloco_sync_period]] |
| `diloco_outer_lr` | Learning rate for DiLoCo's _outer_ optimizer (the one that updates from the synchronized/averaged replica gradients — distinct from each replica's own inner optimizer). | Float, default `0.3`. | [[diloco_outer_lr]] |
| `diloco_outer_momentum` | Momentum for the outer optimizer. | Float, default `0.9`. | [[diloco_outer_momentum]] |
| `dcn_bandwidth_limit` | Per-VM throughput limit for simulating a slow DCN link, e.g. `"10gbit"`. | String, default `""` = no throttling applied. | [[dcn_bandwidth_limit]] |
| `dcn_bandwidth_burst` | Burst-size parameter for the Linux traffic-control (`tc`) token-bucket filter used to implement the throttle. | String, default `"10mb"`. | [[dcn_bandwidth_burst]] |
| `dcn_bandwidth_latency` | Latency parameter for the same `tc` token-bucket filter. | String, default `"50ms"`. | [[dcn_bandwidth_latency]] |
| `dcn_bandwidth_interface` | Network interface the throttling rules are applied to. | String, default `"eth0"`. | [[dcn_bandwidth_interface]] |

## Notes to self

- The `'full'`-is-most-memory-efficient naming trap from Part 5's `remat_policy` has a spiritual cousin here: `opt_type` includes `"muon"` as a first-class option alongside AdamW — worth remembering Muon is genuinely production-viable in MaxText now, not an experimental afterthought, especially paired with QK-Clip (Part 6) which exists specifically to stabilize Muon-trained attention.
- `skip_step_on_spikes` + `trainable_parameters_mask` are both mechanisms that showed up again from Part 6 (DSA indexer warm-up training) — worth noticing MaxText config sections aren't as siloed as the file's own section headers suggest; a full understanding of any one advanced feature (like DSA) usually means pulling threads from three or four different config sections.
- `enable_dropout=false` + fixed seeds = fully reproducible losses is a genuinely useful debugging invariant to know cold — it's the first thing to reach for when trying to determine if a training discrepancy is a real bug or just run-to-run noise.
- DiLoCo's bandwidth-throttling params are explicitly a _simulation_ tool for testing, not a production DiLoCo deployment setting — don't confuse "I'm testing DiLoCo's robustness to bad networks" with "I'm running DiLoCo across two real DCN-separated clusters," even though the same config keys are involved either way.
