### Multi-tier checkpointing (experimental Orbax feature)

Periodically saves to persistent GCS storage on a longer interval, _and_ to a local (host-attached) directory on a shorter interval. On restore, if a local copy exists on any slice, it's broadcast to other slices rather than re-fetched from GCS — much faster recovery from preemption. ([Orbax docs](https://github.com/google/orbax/tree/main/checkpoint/orbax/checkpoint/experimental/emergency/multi_tier_checkpointing))

|Param|Purpose|Options / meaning|
|---|---|---|
|`enable_multi_tier_checkpointing`|Master switch. When enabled, `local_checkpoint_directory` and a non-zero `local_checkpoint_period` must also be set.|`true`/`false`, default `false`.|
|`multi_tier_checkpointing_backup_interval_minutes`|How often (minutes) to back up local checkpoints to GCS. Mutually exclusive with the `_steps` variant below — exactly one must be set when this feature is on.|Positive number or `null`.|
|`multi_tier_checkpointing_backup_interval_steps`|Same, but in training steps instead of wall-clock minutes.|Positive number or `null`.|
|`mtc_data_parallelism`|Number of identical pipelines in the job — should equal `ICI data parallelism × DCN data parallelism`.|Integer, default `0` = auto-set to the number of slices.|

### Emergency checkpointing (experimental Orbax feature)

A simpler variant of the same idea: periodic saves to persistent storage, plus more-frequent local saves, with the same local-broadcast-on-restore behavior. ([Orbax docs](https://github.com/google/orbax/tree/main/checkpoint/orbax/checkpoint/experimental/emergency))

|Param|Purpose|Options / meaning|
|---|---|---|
|`enable_emergency_checkpoint`|Master switch. Requires `local_checkpoint_directory` and a non-zero `local_checkpoint_period`.|`true`/`false`, default `false`.|
|`local_checkpoint_directory`|Local (host) directory for the frequent local saves. Required exactly when `enable_emergency_checkpoint` or `enable_multi_tier_checkpointing` is true.|Path string, default `""`.|
|`local_checkpoint_period`|How often (steps) to save locally. Required (positive) exactly when either feature above is enabled.|Integer, default `0`.|

## The mesh & parallelism system

This is the conceptual core of MaxText's scaling story, so it's worth pausing on the mental model before the parameter tables:

1. **`mesh_axes`** declares the _named dimensions_ of a logical device mesh — e.g. `data`, `fsdp`, `tensor`, `expert`, `context`, `stage`, etc. Every device in your TPU pod slice gets a coordinate along each of these axes.
2. **`logical_axis_rules`** maps _logical_ tensor axes (things like `"activation_batch"`, `"heads"`, `"mlp"`, `"embed"` — named for what they semantically represent in the model) onto one or more of those _physical_ mesh axes. This indirection is what lets the same model code run under totally different parallelism strategies just by changing this config — the model code shards by logical axis name, and this table decides what that means physically.
3. The `ici_*_parallelism` and `dcn_*_parallelism` scalars then set the actual _size_ of each mesh axis — ICI = intra-slice (fast interconnect within one TPU slice/pod), DCN = inter-slice (slower networking between pods/slices, "data center network").

|Param|Purpose|Options / meaning|
|---|---|---|
|`shard_mode`|Whether sharding decisions are automatic (XLA/GSPMD infers them) or explicit (you specify exact shardings).|`"auto"` or `"explicit"`, default `"auto"`.|
|`custom_mesh_and_rule`|Overrides the default mesh + logical-axis-rules wholesale by pointing to a named YAML file under `config/mesh_and_rule/`.|String (a config name) or `""` = use the defaults defined inline in this file.|
|`mesh_axes`|The full list of named physical mesh axes available to shard across.|List, default: `['diloco', 'data', 'stage', 'fsdp', 'fsdp_transpose', 'context', 'context_usp_ulysses', 'context_autoregressive', 'tensor', 'tensor_sequence', 'expert', 'autoregressive']`.|
|`logical_axis_rules`|The full logical→physical axis mapping table (see below).|A large list of `[logical_axis_name, [physical_axes...]]` pairs.|

### `logical_axis_rules` — the pattern, with representative examples

This table is long (~70 entries) and organized into clear sections by model region: **Vocabulary Embedding**, **Attention**, **Mixture of Experts**, **Standard MLP/Dense/Model Structure**, **Inference (Prefill/Decode/Cache)**, and a small **Deprecated** block at the end. Rather than transcribe every line, here's the pattern each section follows, with a representative example or two:

- **Activations** (things flowing through the forward pass) generally shard over `data`/`fsdp`/`context`-family axes for their batch/sequence dimensions, and over `tensor`-family axes for their feature/head dimensions. E.g. `['activation_batch_attn', ['data', 'fsdp', 'fsdp_transpose', 'expert']]` — the attention activation's batch dimension can be sharded across any of those four axes.
- **Weights** generally shard the opposite way — feature/output dimensions over `tensor`-family axes, and input/embedding dimensions over `fsdp`-family axes. E.g. `['heads', ['tensor', 'tensor_sequence', 'autoregressive']]` for attention head weights, or `['mlp', ['fsdp_transpose', 'tensor', 'tensor_sequence', 'autoregressive']]` for dense MLP weights.
- Some logical axes are intentionally left unsharded (mapped to `[]`), e.g. `['qkv', []]`, `['kv', []]`, `['decode_length', []]` — meaning that dimension is always fully replicated, never split across devices.
- A few rules appear **twice** for the same logical axis with slightly different physical-axis lists (e.g. `q_lora` appears once with `fsdp_transpose` included and once without) — MaxText's axis-rule resolution takes the first rule whose physical axes are actually present/active in the current mesh, letting the same logical name degrade gracefully across different mesh configurations.
- Special single-purpose entries exist for things like `['diloco', 'diloco']` (DiLoCo's own dedicated axis), `['engram_dim', ['tensor']]` (DeepSeek Engram, later part), `['layers', 'stage']` (ties the decoder-layer dimension to the pipeline-stage axis), and `['gdn_head', [...]]` (Qwen3-Next's GDN linear-attention heads — noted as sharding like `mlp` during training, but overridden for vLLM serving to match `tpu-inference`'s attention-head ordering).
- The **Deprecated / Scheduled for Removal** block (`mlp_no_fsdp`, `exp_with_fsdp`) is explicitly marked as such in the source — not something to build new configs around.

## DCN & ICI parallelism degrees

The actual size of each mesh axis, split into two families: `dcn_*_parallelism` (across TPU slices, over the data-center network) and `ici_*_parallelism` (within one TPU slice, over the fast inter-chip interconnect). Exactly one axis in each family may be set to `-1` as a placeholder to auto-derive from the available slice/device count — by default, the product of all DCN-axis values should equal the number of slices, and the product of all ICI-axis values should equal the number of devices per slice.

|Axis|DCN default|ICI default|Note|
|---|---|---|---|
|`diloco`|`1`|`1`|For DiLoCo distributed low-communication training.|
|`data`|`-1` (recommended auto-shard axis for DCN)|`1`||
|`fsdp`|`1`|`-1` (recommended auto-shard axis for ICI)||
|`fsdp_transpose`|`1`|`1`||
|`sequence`|`1` (never recommended)|`1`||
|`context`|`1`|`1`||
|`context_usp_ulysses`|`1`|`1`|Ulysses (head-exchange) dimension of context parallelism, used by `context_parallel_strategy='usp'`.|
|`context_autoregressive`|`1`|`1`||
|`tensor`|`1` (never recommended)|`1`||
|`tensor_sequence`|`1` (never recommended)|`1`||
|`pipeline`|`1`|`1`||
|`expert`|`1`|`1`||
|`autoregressive`|`1` (never recommended)|`1`||

Every one of these has a `dcn_*_parallelism` and `ici_*_parallelism` config key (e.g. `dcn_fsdp_parallelism`, `ici_fsdp_parallelism`) — the table above summarizes defaults and which ones the comments explicitly flag as the intended auto-shard axis (`data` for DCN, `fsdp` for ICI) versus axes marked "never recommended" for that network tier (tensor/sequence/autoregressive parallelism over the slow DCN link, in particular, since those need tight interconnect).

Splash Attention is MaxText/Pallas's TPU-optimized flash-attention kernel. These block sizes can be tuned per hardware generation, up to the model's sequence length — again, "profile then tune" territory rather than something to hand-pick blind.

|Param|Purpose|Options / meaning|
|---|---|---|
|`sa_block_q`, `sa_block_kv`, `sa_block_kv_compute`|Query/KV block sizes for the forward pass.|Integers, all default `512`.|
|`sa_block_q_dkv`, `sa_block_kv_dkv`, `sa_block_kv_dkv_compute`|Block sizes for the backward pass w.r.t. K/V.|Integers, all default `512`.|
|`sa_block_q_dq`, `sa_block_kv_dq`|Block sizes for the backward pass w.r.t. Q.|Integers, both default `512`.|
|`sa_use_fused_bwd_kernel`|Uses a fused backward-pass kernel.|`true`/`false`, default `false`.|
|`sa_bwd_dkv_megacore`|Enables megacore-parallel KV-head groups in the static dKV grid (a TPU megacore scheduling detail).|`true`/`false`, default `false`.|
|`sa_q_layout`, `sa_k_layout`, `sa_v_layout`|Memory layout for Q/K/V tensors in the kernel.|String, default `"HEAD_DIM_MINOR"` for all three.|
|`use_splash_scheduler`|Uses the Tokamax splash-attention scheduler.|`true`/`false`, default `false`.|
|`ring_scan_unroll`|Unroll factor for Tokamax ring-attention scans.|Integer, default `1`; `0` or ≥ the ring size fully unrolls.|
|`sa_fuse_reciprocal`|Fuses the reciprocal (division) operation in the softmax computation.|`true`/`false`, default `true` (Tokamax's default).|

## Notes to self

- The logical-axis-rules indirection is the single most important idea in this whole part: it's _why_ the same MaxText model code can run unchanged from a single TPU chip up to a full pod slice with FSDP+tensor+expert+pipeline+context parallelism all composed together — only this table (and the `ici_*`/`dcn_*` sizes) needs to change, not the model.
- ICI vs. DCN is really "parallelism strategies that need fast interconnect" vs. "parallelism strategies that can tolerate slower cross-slice networking" — data parallelism tolerates DCN fine (hence it's the recommended DCN auto-shard axis), while tensor/sequence/autoregressive parallelism explicitly should **not** go over DCN (marked "never recommended" in the source) because they need the tight synchronization only ICI provides.
- Splash-attention block sizes and the DCN/ICI parallelism degrees are exactly the kind of thing you'd want a sweep/benchmark harness for on your specific TPU generation — not something to reason your way to analytically before profiling.
