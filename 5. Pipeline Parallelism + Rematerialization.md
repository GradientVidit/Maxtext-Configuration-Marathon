## Pipeline parallelism (PP)

The core identity to hold in your head for this whole block: **`num_decoder_layers = num_stages × num_layers_per_pipeline_stage × num_pipeline_repeats`**. Everything else here is tuning how that product gets split up and scheduled.

There's a real trade-off embedded in these settings: more layers per stage makes it easier to hide pipeline communication behind compute (more compute per stage to overlap with), but produces a _larger bubble_ (idle time) since there are fewer repeats to amortize it over. Similarly, more microbatches shrinks the bubble but shrinks each microbatch's size, which can hurt per-stage compute efficiency. The bubble fraction itself is `(num_stages - 1) / (num_pipeline_repeats * num_pipeline_microbatches + num_stages - 1)`.

|Param|Purpose|Options / meaning|Deep Dive|
|---|---|---|---|
|`num_layers_per_pipeline_stage`|How many decoder layers live on each pipeline stage.|Integer, default `1`.|[[num_layers_per_pipeline_stage]]|
|`num_pipeline_repeats`|How many times the full stage cycle repeats. Computed as `num_decoder_layers / (num_stages * num_layers_per_pipeline_stage)` when left at default.|Integer, default `-1` = auto-derived.|[[num_pipeline_repeats]]|
|`pipeline_parallel_layers`|Pipeline only this many layers; remaining layers instead use the "stage" mesh axis as plain data parallelism. Useful when the total layer count doesn't divide cleanly by the PP degree (SPMD pipelining requires PP degree to evenly divide the layer count).|Integer, default `-1` = pipeline all decoder layers.|[[pipeline_parallel_layers]]|
|`num_pipeline_microbatches`|Number of microbatches per pipeline iteration; must be a multiple of `num_stages`. Microbatch size = `global_batch_size / num_pipeline_microbatches`, where `global_batch_size = per_device_batch_size * num_devices`.|Integer, default `-1` = set equal to `num_stages`.|[[num_pipeline_microbatches]]|
|`pipeline_delay_activation_forwarding`|Delays activation forwarding by one loop iteration, decoupling that iteration's communication from its compute so XLA can overlap them independently — at the cost of _doubling_ the pipeline bubble. Requires `num_pipeline_microbatches ≥ 2 * num_stages` (enforced as the new minimum when this is enabled).|`true`/`false`, default `false`.|[[pipeline_delay_activation_forwarding]]|
|`pipeline_fsdp_ag_once`|All-gathers all FSDP-sharded weights once, before the first pipeline iteration, instead of once per microbatch. Trades memory (must hold the fully-gathered weights + gradients, typically bf16) for less communication (one all-gather/reduce per repeat instead of per microbatch — similar in spirit to ZeRO-1, since the backward pass also skips re-gathering). An alternative the comments suggest: use DP instead of FSDP where possible, plus optimizer offloading if memory is tight.|`true`/`false`, default `false`.|[[pipeline_fsdp_ag_once]]|
|`pipeline_fsdp_ag_per_repeat`|Advanced pipeline weight-prefetching: prefetches weight gathers ahead of the microbatched computation per repeat, reducing collective-communication overhead.|`true`/`false`, default `false`.|[[pipeline_fsdp_ag_per_repeat]]|

### PP scan/remat loop structure

Pipeline parallelism has two nested loops: an **outer loop over microbatches** (pipeline iterations) and an **inner loop over layers** (layers per stage). The maintainers note that applying both scanning _and_ a remat policy to both loops causes extra rematerialization, and recommend the defaults below — scan and remat policy applied only to the outer (pipeline-iteration) loop. The reverse may be worth trying when `num_layers_per_pipeline_stage` is very large. These five settings only matter when pipeline parallelism is actually in use.

|Param|Purpose|Options / meaning|Deep Dive|
|---|---|---|---|
|`scan_pipeline_iterations`|Whether to `jax.lax.scan` over pipeline iterations (the outer loop).|`true`/`false`, default `true` (recommended).|[[scan_pipeline_iterations]]|
|`scan_pipeline_repeats`|Whether to scan over pipeline repeats.|`true`/`false`, default `false`.|[[scan_pipeline_repeats]]|
|`scan_layers_per_stage`|Whether to scan over the layers-per-stage (inner loop).|`true`/`false`, default `false`.|[[scan_layers_per_stage]]|
|`set_remat_policy_on_pipeline_iterations`|Whether to apply the remat policy on the outer (pipeline-iteration) loop.|`true`/`false`, default `true` (recommended).|[[set_remat_policy_on_pipeline_iterations]]|
|`set_remat_policy_on_layers_per_stage`|Whether to apply the remat policy on the inner (layers-per-stage) loop.|`true`/`false`, default `false`.|[[set_remat_policy_on_layers_per_stage]]|

## Rematerialization (activation checkpointing)

Rematerialization ("remat") is activation checkpointing: instead of keeping every intermediate activation in memory for the backward pass, you discard some and recompute them on the fly — trading extra forward-pass compute for lower peak HBM usage. This is one of the most impactful config sections for whether a given model+batch-size actually fits in memory at all.

|Param|Purpose|Options / meaning|Deep Dive|
|---|---|---|---|
|`remat_policy`|Selects a _preset_ remat policy — how aggressively to discard vs. keep activations. Presets trade off speed (fastest → slowest) against HBM usage (highest → lowest usage).|One of: `'minimal_with_context'`, `'minimal'`, `'save_dot_with_context_except_mlp'`, `'save_dot_except_mlpwi'`, `'save_dot_except_mlp'`, `'save_qkv_proj'`, `'qkv_proj_offloaded'`, `'custom'`, `'minimal_offloaded'`, `'save_out_proj'`, `'full'`. Default `'full'` (recomputes the most, keeps the least in memory — slowest but most memory-efficient end of the spectrum, despite the name suggesting otherwise: "full" rematerialization, not "full" activation retention).|[[remat_policy]]|

### Custom remat policy — per-tensor placement

When `remat_policy: 'custom'` is chosen, each of the following tensors can individually be assigned one of three placements: **`'remat'`** (discard and recompute during backward), **`'device'`** (keep resident in device/HBM memory), or **`'offload'`** (move to host memory and bring back when needed). This lets you hand-tune exactly which tensors are worth keeping around vs. recomputing vs. offloading, rather than accepting one of the coarse presets above.

|Tensor|Notes|Default placement|
|---|---|---|
|`decoder_layer_input`|Cannot be rematerialized — it serves as the periodic checkpoint that acts as the remat _start point_ for everything else.|`'device'`|
|`indexer_cutoff_threshold`|Indexer cutoff threshold tensor (relevant to sparse-attention indexer mechanisms, Part 6).|`'remat'`|
|`context`|Per [TransformerEngine's attention implementation](https://github.com/NVIDIA/TransformerEngine/blob/main/transformer_engine/jax/attention.py#L581-L583).|`'remat'`|
|`mlpwi`, `mlpwi_0`, `mlpwi_1`, `mlpwo`|Dense MLP up/gate/down-projection intermediates.|`'remat'`|
|`moe_mlpwi_0`, `moe_mlpwi_1`, `moe_mlpwo`|MoE-equivalent MLP projection intermediates.|`'remat'`|
|`query_proj`, `key_proj`, `value_proj`, `kv_proj`, `qkv_proj`, `out_proj`|Standard attention projection intermediates.|`'remat'`|
|`query_wa_proj`, `kv_wa_proj`|Weight-absorbed query/KV projections (an MLA optimization, Part 6).|`'remat'`|
|`mla_q`, `mla_kv`|MLA-specific query/KV intermediates (Part 6).|`'remat'`|
|`attention_out`|Attention block output.|`'remat'`|
|`engram`|Engram-module intermediate (DeepSeek Engram, a later part).|`'remat'`|

## Notes to self

- The `num_stages × num_layers_per_pipeline_stage × num_pipeline_repeats = num_decoder_layers` identity is worth memorizing cold — it's the first thing to check when PP config isn't behaving as expected.
- `remat_policy: 'full'` being the _most_ memory-efficient (not least) despite sounding like "keep everything" is a genuine naming trap — it means "fully rematerialize" not "fully retain in memory." Worth double-checking this every time you touch it.
- `scan_layers=true` normally, but `false` when doing pipeline parallelism, is a subtlety easy to miss if you're porting a non-PP config to a PP setup (or vice versa) — the checkpoint-metadata auto-detection is a safety net, but only for _resuming_, not for a fresh run.
- The custom remat per-tensor table is effectively a menu of every major intermediate tensor in the forward pass across dense attention, MLA, MoE, and Engram — useful as a checklist for understanding _what the model actually materializes_ at each layer, independent of the remat question.
