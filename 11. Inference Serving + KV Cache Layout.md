
This part covers MaxText's inference/serving-side config — benchmarking tools, the disaggregated-serving setup, cache/compute tensor layouts, and some general debug/logging switches that happen to live in this part of the file.

## KV cache & compute tensor layout

These control the physical axis ordering of the KV cache and compute tensors — a performance-tuning detail about memory layout, not a correctness one (the logical meaning of each axis is unchanged; only its physical position in the tensor shape changes).

| Param | Purpose | Options / meaning | Deep Dive |
|---|---|---|---|
| `prefill_cache_axis_order` | Physical axis order for the KV cache during prefill. Logical layout is `0,1,2,3 = CACHE_BATCH, CACHE_SEQUENCE, CACHE_HEADS, CACHE_KV`; the default reorders this. | String of axis indices, default `"1,2,0,3"` (i.e. `CACHE_SEQUENCE, CACHE_HEADS, CACHE_BATCH, CACHE_KV`). | [[prefill_cache_axis_order]] |
| `ar_cache_axis_order` | Same, for the autoregressive (decode-step) KV cache. | String, default `"1,2,0,3"`. | [[ar_cache_axis_order]] |
| `compute_axis_order` | Physical axis order for compute tensors generally. Logical layout is `0,1,2,3 = BATCH, LENGTH, HEAD, D_KV`. Only two orderings are currently supported. | `"0,1,2,3"` (default) or `"0,2,1,3"`. | [[compute_axis_order]] |
| `reshape_q` | Whether to reshape the query tensor at a specific point in attention computation — an implementation/performance detail tied to the layout choices above. | `true`/`false`, default `false`. | [[reshape_q]] |

## Notes to self

- The cache/compute axis-order params are a good example of a config surface that's easy to misread as "pick whichever" when it's actually tightly constrained — `compute_axis_order` explicitly only supports two of the 24 possible permutations of 4 axes, because the rest presumably don't have corresponding optimized kernels.
- `prefill_slice`/`generate_slice` being independently settable is the config-level expression of disaggregated serving — prefill (compute-bound, benefits from bigger/more chips briefly) and decode (memory-bandwidth-bound, benefits from being spread thin over many small requests) have different optimal hardware shapes, so production serving setups often split them onto separate slices entirely.
- This part, more than most others, is squarely inference/serving territory rather than pretraining territory — useful to know it's here, but day-to-day pretraining config work is unlikely to touch most of these.
